## 1. Executive Summary

Phase 3 converts the Phase 2 MVP into a pilot-ready platform by adding the capabilities that create measurable value for farmers and buyers:

- Mobile-money payment initiation and callback handling
- Payment reconciliation, reminders, overdue states, and dispute records
- Initial price and harvest-timing forecasts using approved data sources
- Transport request matching and shared-load pooling
- Security, reliability, observability, and data-quality controls
- Pilot support tools, training materials, and release-candidate validation

The phase is complete when a test user can move through the full marketplace journey, including payment, while the system produces an explainable forecast and a transport recommendation using representative Central Region data.

### Phase 3 Outcomes

| Outcome | Target |
|---|---|
| Payment integration | Sandbox payment flow succeeds for both success and failure callbacks |
| Reconciliation | Every payment has an auditable status and provider reference |
| Reminders | Due and overdue notifications are generated by a repeatable job |
| Forecasting | Price trend and sell-now/wait recommendations available with confidence indicators |
| Transport | Requests can be matched and pooled within the agreed geographic radius |
| Reliability | Monitoring, backups, rollback, and incident procedures documented |
| Security | Secrets removed from source; access and webhook validation controls enabled |
| Pilot readiness | Release candidate passes end-to-end, security, performance, and field usability checks |

### Scope Boundary

**Included:** MVP payment integration, baseline forecasting, transport pooling, security hardening, operational readiness.  
**Deferred:** Automated credit scoring, advanced ML retraining pipelines, full logistics dispatch, multi-country support, and complex dispute arbitration.

## 3. Workstream 3.1: Mobile-Money Payments

**Duration:** Weeks 13–16  
**Owner:** Backend Lead  
**Goal:** Make payment status trustworthy, traceable, and safe to retry.

### Payment State Machine

```text
pending -> initiated -> processing -> completed
                         |             |
                         v             v
                       failed       disputed
pending/processing -> overdue
```

Rules:

- Provider callbacks are idempotent and may be received more than once.
- A completed payment cannot return to pending.
- Provider references are unique.
- Amount and currency are checked against the transaction before completion.
- Every state change records actor, timestamp, source, and reason.
- The system never marks a payment completed solely from a client-side response.

### Week 13: Provider Adapter and Payment Model

**Monday–Tuesday (Days 1–2): Payment Contract Review**

Tasks:

1. Review the selected provider's API, authentication, callback, timeout, and retry rules.
2. Confirm supported mobile-money networks and test account requirements.
3. Document fees, settlement timing, transaction limits, and customer support escalation.
4. Define payment API contract independently of the provider.
5. Define callback signature and replay-protection requirements.

**Deliverable:** Approved payment integration specification  
**Owner:** Backend Lead + Integration Engineer

**Wednesday–Friday (Days 3–5): Payment Adapter and Schema**

Tasks:

1. Create a provider adapter interface with `initiate`, `verify`, and `parseCallback` operations.
2. Add payment fields to the transaction model: provider, provider reference, currency, initiated time, completed time, failure reason, and callback hash.
3. Implement a mock provider for deterministic automated tests.
4. Add configuration validation for provider credentials.
5. Define migration DDL for the future PostgreSQL payment tables.

**Deliverable:** Provider-neutral adapter, model update, mock gateway, and migration draft  
**Owner:** Backend Engineers

### Week 14: Initiation, Callbacks, and Reconciliation

**Monday–Wednesday (Days 6–8): Payment Initiation**

Tasks:

1. Implement `POST /api/transactions/:id/pay` as an initiation endpoint.
2. Validate transaction ownership, amount, currency, and current state.
3. Generate an idempotency key for each payment attempt.
4. Return a user-safe status without exposing provider credentials or internal errors.
5. Add USSD and app confirmation messages for initiated payments.

**Deliverable:** Payment initiation works against the mock provider and sandbox  
**Owner:** Backend Lead

**Thursday–Friday (Days 9–10): Callback and Verification Handling**

Tasks:

1. Add a provider callback route with signature or token validation.
2. Reject malformed, expired, or duplicated callbacks safely.
3. Verify the provider reference before completing the transaction.
4. Add retry-safe notification triggers for completed and failed payments.
5. Record all callback attempts in an audit log.

**Deliverable:** Success, failure, duplicate, and invalid callback cases tested  
**Owner:** Integration Engineer + QA

### Week 15: Reminders, Reconciliation, and Disputes

**Monday–Tuesday (Days 11–12): Payment Jobs**

Tasks:

1. Implement a repeatable job for payments due soon.
2. Implement overdue detection using the agreed grace period.
3. Ensure rerunning the job does not duplicate notifications.
4. Add `POST /api/transactions/reminders/run` authorization and audit logging.
5. Add dashboard counts for pending, completed, overdue, and disputed payments.

**Deliverable:** Reminder and overdue jobs work on seeded transactions  
**Owner:** Backend Engineer

**Wednesday–Thursday (Days 13–14): Reconciliation**

Tasks:

1. Compare local payment records with provider test results.
2. Create a reconciliation report showing matched, unmatched, and pending references.
3. Define manual reconciliation procedure for provider downtime.
4. Add an operations view or export for unresolved payments.
5. Test partial outages and delayed callbacks.

**Deliverable:** Reconciliation report and operations procedure  
**Owner:** Finance/Operations Lead + Backend Lead

**Friday (Day 15): Dispute Handling**

Tasks:

1. Add a dispute record or transaction dispute fields.
2. Define who can open, review, resolve, and close a dispute.
3. Prevent disputed transactions from being silently overwritten.
4. Add notification templates for dispute opened and resolved.
5. Document evidence requirements and escalation contacts.

**Deliverable:** Dispute workflow documented and tested  
**Owner:** Product Lead + Backend Lead

### Week 16: Payment Acceptance and Security Testing

**Monday–Wednesday (Days 16–18): End-to-End Payment Testing**

Test scenarios:

- Successful payment
- Declined payment
- Provider timeout
- Duplicate initiation request
- Duplicate callback
- Incorrect amount
- Incorrect currency
- Expired transaction
- Overdue payment
- Disputed payment
- Provider unavailable

**Deliverable:** Payment test report with zero unresolved P0/P1 defects  
**Owner:** QA Lead

**Thursday (Day 19): Security Review**

Tasks:

1. Verify callback authentication and replay protection.
2. Check logs for phone numbers, tokens, and payment data exposure.
3. Confirm secrets are supplied through environment configuration.
4. Test authorization for payment, reminder, and dispute operations.
5. Review rate limits and abuse handling.

**Deliverable:** Payment security review signed off  
**Owner:** Security/DevOps Lead

**Friday (Day 20): Payment Gate**

The payment workstream passes when:

- [ ] The provider sandbox completes a full payment flow.
- [ ] Local status is updated only from verified provider information.
- [ ] Callbacks are authenticated and idempotent.

- [ ] Reconciliation and dispute procedures are usable by operations staff.

## 4. Workstream 3.2: Forecasting and Decision Support

**Duration:** Weeks 13–17  
**Owner:** Data/ML Lead  
**Goal:** Provide useful, explainable guidance without presenting uncertain predictions as guarantees.

### Forecasting Principles

- Start with interpretable baselines before introducing complex models.
- Display the data date, forecast horizon, confidence, and known limitations.
- Never recommend a decision when required data is missing or stale.
- Store model version and input snapshot with every generated forecast.
- Compare forecasts with actual prices and harvest outcomes during Phase 5.

### Week 13: Data Inventory and Forecast Definition

**Monday–Wednesday (Days 1–3): Data Audit**

Tasks:

1. Inventory baseline price data, market names, dates, units, and sources.
2. Identify missing values, duplicate observations, inconsistent crop names, and outliers.
3. Normalize market and crop identifiers.
4. Confirm data licensing and permitted retention.
5. Define a minimum data-quality threshold for publishing a forecast.

**Deliverable:** Cleaned data dictionary and quality report  
**Owner:** Data/ML Lead + Field Researcher

**Thursday–Friday (Days 4–5): Recommendation Specification**

Define:

- Current price and recent average
- Four-week trend direction
- Expected price range, if sufficient data exists
- Sell-now, wait, or gather-more-data recommendation
- Harvest timing recommendation based on harvest date and price signal
- Confidence label: high, medium, or low

**Deliverable:** Product-approved forecast response contract and explanation text  
**Owner:** Product Lead + Data/ML Lead

### Week 14: Baseline Models

**Monday–Wednesday (Days 6–8): Price Trend Baseline**

Tasks:

1. Implement moving-average and change-from-baseline calculations.
2. Add minimum observation and recency checks.
3. Calculate direction using a documented threshold to avoid noisy signals.
4. Produce a chart-ready series for the app and dashboard.
5. Build fixtures for rising, stable, falling, and insufficient-data cases.

**Deliverable:** Deterministic price-trend service with tests  
**Owner:** Data Engineer

**Thursday–Friday (Days 9–10): Sell-Now-vs-Wait Baseline**

Tasks:

1. Combine price trend, harvest date, quantity, and perishability assumptions.
2. Return recommendation plus plain-language reasons.
3. Include a conservative default when the forecast confidence is low.
4. Expose model version and generated timestamp.
5. Review recommendations with an agronomy or field expert.

**Deliverable:** First recommendation engine approved for staging  
**Owner:** Data/ML Lead + Agronomy Advisor

### Week 15: Forecast API and Interfaces

**Monday–Tuesday (Days 11–12): Forecast API**

Tasks:

1. Add forecast service endpoints under the existing API convention.
2. Validate crop, market, date range, and quantity inputs.
3. Return current data, forecast output, confidence, and explanation.
4. Add response caching with a short expiry for repeated requests.
5. Add logging without recording unnecessary personal data.

**Deliverable:** Forecast API documented and available in staging  
**Owner:** Backend Engineer

**Wednesday–Thursday (Days 13–14): Mobile and Dashboard Integration**

Tasks:

1. Add forecast card to the price screen.
2. Show confidence and data freshness next to the recommendation.
3. Add dashboard view for forecast requests and model status.
4. Provide a clear unavailable state when data quality is insufficient.
5. Test on low-bandwidth responses and small screens.

**Deliverable:** Forecast guidance visible in app and dashboard  
**Owner:** Mobile Lead + Frontend Lead

**Friday (Day 15): Expert Review**

Tasks:

1. Review at least 20 historical examples with a field expert.
2. Identify misleading, overly confident, or unusable recommendations.
3. Adjust thresholds and explanations where evidence supports it.
4. Record unresolved limitations for pilot training.

**Deliverable:** Forecast review log and approved changes  
**Owner:** Data/ML Lead

### Week 16: Evaluation and Data Pipeline

**Monday–Wednesday (Days 16–18): Backtesting**

Tasks:

1. Split historical data into training/reference and evaluation periods.
2. Compare baseline forecast to a naive recent-price baseline.
3. Calculate MAE or equivalent error measure where data permits.
4. Measure recommendation accuracy separately from price error.
5. Publish results with sample size and confidence limitations.

**Deliverable:** Forecast backtest report  
**Owner:** Data/ML Lead

**Thursday–Friday (Days 19–20): Data Refresh Procedure**

Tasks:

1. Define how new market observations are collected and approved.
2. Add duplicate and unit validation.
3. Define refresh frequency and stale-data alerts.
4. Document manual correction and rollback steps.
5. Create a model/data version record.

**Deliverable:** Forecast data operations runbook  
**Owner:** Data Engineer + Operations Lead

### Week 17: Forecast Hardening

**Tasks:**

## 5. Workstream 3.3: Transport Matching and Pooling

**Duration:** Weeks 14–17  
**Owner:** Backend Lead + Operations Lead  
**Goal:** Match transport requests and identify shared-load opportunities while keeping the first version understandable to dispatchers.

### Pooling Rules

- Match compatible crop type, pickup area, destination area, date window, and quantity.
- Use the Phase 1 agreed geographic radius, initially 5 km for pickup clustering.
- Never exceed vehicle capacity.
- Show why requests were grouped and allow an operator to reject a suggestion.
- Keep the algorithm deterministic and log the inputs used for each recommendation.

### Week 14: Matching Specification

Tasks:

1. Confirm transport request fields and required units.
2. Define destination and pickup normalization rules.
3. Define vehicle capacity and transporter availability fields.
4. Agree on acceptable date and distance tolerances.
5. Create sample requests covering match, no-match, and capacity cases.

**Deliverable:** Pooling rules, examples, and acceptance criteria  
**Owner:** Operations Lead

### Week 15: Matching Service

Tasks:

1. Implement request filtering by status and time window.
2. Implement geographic distance calculation using stored coordinates.
3. Group compatible requests by origin, destination, crop, and date.
4. Split groups when capacity is exceeded.
5. Return estimated shared cost and per-request allocation.
6. Add tests for boundary distance and capacity conditions.

**Deliverable:** Deterministic pooling service with unit tests  
**Owner:** Backend Engineer

### Week 16: Assignment and Notifications

Tasks:

1. Connect match suggestions to transporter assignment flow.
2. Add accept, reject, and cancel states.
3. Notify affected farmers, buyers, and transporters through the existing notification service.
4. Prevent assignment of unavailable transporters.
5. Record assignment history and operator actions.

**Deliverable:** Transport request-to-assignment flow working in staging  
**Owner:** Backend Lead + Operations Lead

### Week 17: Operational Validation

Tasks:

1. Run the algorithm against representative Central Region requests.
2. Compare pooled and unpooled cost estimates.
3. Review recommendations with transport partners.
4. Measure match rate, capacity utilization, and estimated savings.
5. Document manual override procedures.

**Deliverable:** Transport validation report and operator runbook  
**Owner:** Operations Lead + QA

## 8. Testing Strategy

### Automated Tests

- Unit tests for payment state transitions and idempotency.
- Callback signature, replay, and malformed-payload tests.
- Forecast calculations for all trend and data-quality cases.
- Pooling distance, capacity, date, and cost tests.
- Authorization tests for all protected operations.
- Job repeatability tests for reminders and data refreshes.

### Integration Tests

- Mock provider success, failure, timeout, and duplicate callback.
- Staging provider payment with verified reference.
- Forecast API to mobile and dashboard response rendering.
- Transport request to assignment and notification flow.
- Service restart during pending payment and job execution.

### Field-Oriented Tests

- USSD payment status check on a feature phone.
- App payment initiation on a slow network.
- Forecast explanation understood by at least three pilot representatives.
- Transport recommendation reviewed by at least two transport partners.
- SMS content checked for length, clarity, and correct phone recipient.

### Quality Targets

| Area | Target |
|---|---|
| Payment state tests | 100% of defined transitions covered |
| Protected endpoint authorization | 100% of sensitive routes tested |
| Forecast response | p95 under 1 second for cached/reference data |
| Payment callback handling | Duplicate callbacks create no duplicate transaction effect |
